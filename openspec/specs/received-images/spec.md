## Requirements
### Requirement: Live direct-chat image activity
The system SHALL display newly emitted supported image messages from connected-session `notify` upserts in the live activity panel. It SHALL include incoming one-to-one contact images and image events marked `fromMe` only when they belong to the linked account's own self-chat. The activity item SHALL show a preview and any available caption, direction, time, and conversation label. The system SHALL NOT request or present historical image messages as live activity.

#### Scenario: Incoming contact image with caption
- **WHEN** a connected session emits a `notify` image message for a direct contact chat with a caption
- **THEN** the panel displays an image preview and the available caption, direction, time, and conversation label

#### Scenario: Incoming image without text
- **WHEN** a connected session emits a supported direct-chat image without a caption or text body
- **THEN** the panel still displays an image activity item and does not require a text body

#### Scenario: Image sent in linked account self-chat
- **WHEN** a connected session emits an image event marked `fromMe` whose remote chat is the linked account's own self-chat
- **THEN** the panel displays the image preview as a self-chat event

#### Scenario: Group, non-notify, or historical image
- **WHEN** an image belongs to a group, status, newsletter, a non-`notify` upsert, or historical synchronization
- **THEN** the system does not save it or present it as new live activity

#### Scenario: Non-image attachment
- **WHEN** a direct-chat event contains a document, video, audio, or sticker rather than an image
- **THEN** the system does not save it or present it as an image preview

### Requirement: Isolated flat image storage
The system SHALL save each supported image original beneath the local `./received-images/` root in one flat folder per normalized active-account JID and normalized remote-chat JID. The folder name SHALL include the account ID, chat ID, and a sanitized WhatsApp user-name suffix; the account/chat IDs SHALL be the isolation key, so duplicate or changed names SHALL NOT mix or split conversation storage. Image files SHALL be stored directly in that folder without date, media-type, or other nested subfolders. Filenames SHALL be generated by the application and SHALL NOT use a message-supplied filename or path.

#### Scenario: Separate contacts under one account
- **WHEN** images arrive from two direct chats with different remote chat IDs under the same linked account
- **THEN** each image is saved in its own conversation folder and the files are not mixed

#### Scenario: Same contact under another linked account
- **WHEN** the same remote chat ID receives an image after a different WhatsApp account is linked
- **THEN** the image is saved in a different account-specific conversation folder

#### Scenario: Duplicate or changed display name
- **WHEN** two chats have the same WhatsApp user name, or a chat's displayed name changes
- **THEN** account/chat IDs continue to select distinct, stable folders

#### Scenario: Flat folder layout
- **WHEN** a supported image is saved
- **THEN** its file is placed directly in the account/conversation folder and no nested date or media folder is created

#### Scenario: Unsafe or missing display name
- **WHEN** a WhatsApp user name is missing or contains filesystem-special characters
- **THEN** the system uses a safe fallback or sanitized suffix without changing the account/chat isolation key

### Requirement: Persistent image retention
The system SHALL retain saved image files across session logout, account switching, and process restart until the owner manually removes them. Clearing or evicting an activity event SHALL NOT delete its image file. The live panel SHALL NOT restore old image events from disk after restart. The system SHALL NOT impose an application-defined per-image size cap and SHALL stream media to disk rather than requiring the full original in application memory.

#### Scenario: Logout clears only transient activity
- **WHEN** the owner logs out of a WhatsApp account
- **THEN** the in-memory activity feed is cleared while saved image files remain in their account-specific folders

#### Scenario: Process restart
- **WHEN** the application restarts
- **THEN** saved image files remain on disk, but the prior live activity feed is not restored

#### Scenario: Owner manually removes image files
- **WHEN** the owner deletes saved files from the local image-storage folders
- **THEN** the system does not recreate those files unless it receives and saves the corresponding image again

#### Scenario: Supported large image
- **WHEN** a valid supported image exceeds a hypothetical application size threshold
- **THEN** the system does not reject it solely for that threshold and streams the image to disk

### Requirement: Private preview delivery
The system SHALL serve saved previews through a same-origin read-only route addressed by an opaque media ID. Activity events SHALL NOT include image bytes, local filesystem paths, account JIDs, or remote-chat JIDs. The media route SHALL resolve only IDs registered by the server-side image store, SHALL return only validated image content, and SHALL NOT permit a client to select an arbitrary filesystem path.

#### Scenario: Panel loads a saved preview
- **WHEN** the panel requests a valid media ID belonging to a saved image
- **THEN** the local server returns that image with its validated image content type and no-store caching headers

#### Scenario: Unknown media ID or path traversal attempt
- **WHEN** a request uses an unknown ID, a path-like ID, or traversal characters
- **THEN** the server rejects the request without reading or returning an arbitrary file

#### Scenario: Activity event is broadcast
- **WHEN** an image activity item is sent through the event stream
- **THEN** it contains only the event metadata and opaque preview URL, not media bytes, filesystem paths, or chat/account identifiers

### Requirement: Isolated image receive failures
The system SHALL handle media download, validation, and storage failures without interrupting existing text-command processing. It SHALL show a generic unavailable state for an image that could not be saved or previewed and SHALL NOT write message content, media bytes, chat identifiers, filesystem paths, or raw media errors to routine diagnostics.

#### Scenario: Media download fails
- **WHEN** Baileys cannot download or decrypt an image
- **THEN** the panel displays a generic unavailable image state, command processing continues, and routine diagnostics reveal no raw error or private message data

#### Scenario: Image write fails
- **WHEN** the local filesystem rejects an image write
- **THEN** the panel displays a generic unavailable image state, command processing continues, and no incomplete file is presented as a saved image
